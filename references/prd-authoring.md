# PRD 写法与交付检查

用于按原型补全、精简功能表或沿用作者示例。先取作者的组织方式，再处理具体规则；示例中的阈值、邮箱、角色和上传策略只属于原项目。

## 默认成稿样式

- **功能表为主体**：背景简短，功能规则用短句逐项写；条件或异常确实复杂时再展开。
- **标题连续编号**：按 `1 → 1.1 → 1.1.1` 标出层级，检查跳号、重号及目录显示。
- **突出重点**：对关键条件、动作、范围和限制加粗；配合标题与编号帮助跳读，避免整段加粗。
- **按需填写章节**：默认先不写埋点；已有功能表说清的内容不另起长篇重复。验收按功能归并，保留必要边界与失败处理。

## 章节与版本

沿用本次文档的结构和明确取舍。常见章节这样填写：

| 部分 | 填写口径 |
|---|---|
| 前言、背景 | 简述当前问题、用户需要及本次目标，避免重复功能表 |
| 版本信息、变更日志 | 记录这篇文档的版本；保留人工填写的版本、作者和历史，原型版本放在原型说明中 |
| 需求范围 | 列涉及的端及职责，如 APP（Android／iOS）、设备、服务端；页面状态清单放到原型部分 |
| 功能说明 | 作为规则主体，条件、操作、结果和例外逐条写清 |
| 流程图、原型 | 涉及流程或界面变化时填写，与功能规则对应 |
| 验收、非功能要求 | 写可观察的结果和本次实际约束 |
| 埋点、项目规划、附录 | 埋点待本次明确要求再写；其他章节按已有要求和资料填写。工时留给研发评估，版本约束和日期仅记录已确认内容 |

有新原型或用户回复时，先核对基线和冲突。已删除、划线作废的旧规则不从历史材料补回；无法确定时提出具体问题，继续不依赖答案的部分。

## 功能表的分层写法

- 模块：指出哪个部分，例如“记录选择”。
- 功能：一句话交代用途，例如“勾选需上传的记录”。
- 详细说明：先按区域或规则分组，再用 `1 → a → i` 展开。一条只承载一个可判断的规则；不为凑层级增加空标题。
- 重点：只将关键条件、禁止项和保留规则加粗，使用默认黑色。
- 交互图：本行放对应区域或状态的实际截图，尺寸以文字可辨、无裁切为准。

精简的目标是易读且完整。把重复表达删掉，不把多条规则重新挤成一段；字数减少本身不能证明需求完整。检查否定、数量、时间、选填／必填、保留／清空及失败后的处理是否仍明确。

例如，若本次已确认跨筛选保留选择，可以写成：

```xml
<ol>
  <li>选择方式<ol>
    <li>支持单条勾选、取消勾选。</li>
    <li><b>全选、取消全选仅影响当前筛选结果。</b></li>
    <li>全选框显示未选、半选、全选状态。</li>
  </ol></li>
  <li>切换筛选<ol>
    <li><b>保留已选记录及对应备注。</b></li>
  </ol></li>
  <li>数量展示<ol>
    <li>显示全部已选记录数。</li>
    <li>另提示当前筛选外的已选数量。</li>
  </ol></li>
</ol>
```

子 `<ol>` 位于父 `<li>` 内，编号由飞书生成。需要三级时同样嵌套，写入后检查实际 `seq-marker` 和页面层级。

正式中文成稿使用可用的 `humanizer-zh` 审校；不可用时手工核对简洁性、语域与信息完整性。正文保留产品需求、待确认规则和必要的原型演示说明，制作过程、工具选择和测试日志放在交付记录中。

## HTML、截图与流程图

**共享区域与角色增量。** 原型中某角色是在通用页面下方增加内容时，把共享区作为持续存在的页面部分。切换页签、筛选、详情、上传进度和结果时，检查共享输入、按钮和联系信息仍在，未提交内容仍保留。检查最终 HTML 附件，不能只验证本地旧文件。

**有状态操作。** 按本次已确认规则检查筛选前后选择、备注、全选作用范围、跨筛选统计、取消、失败重试和恢复。用本地存储或计时器演示续传、锁屏上传时，说明它是演示；真实 APP 后台能力需实机验证。

**截图与附件各司其用。** 表格截图帮助逐项核对，HTML 附件用于交互。HTML 修改后重新生成受影响截图，核对最终附件的文件名、大小及预览交互，避免图片和附件版本错位。

**流程图保持业务连续。** 先确认主流程及角色／权限判断。用户要求合并时，把各段接成一条完整流程，包含关键判断、成功、失败和恢复分支。使用原生画板；静态预览或 SVG 导入成功不等于节点可编辑，需实际检查节点编辑能力。

**流程图先整理连线。** 沿用相邻流程图的节点、颜色、字体和连线风格，优先在同一张图内优化布局。主线保持同一方向，节点文案只写动作或判断；分支就近放置，标清条件，用短折线或带含义的连接节点减少长回线，避开穿字和穿节点。图的拆合遵从用户要求，不能自行把单图换成多图或换新风格，也不能删掉异常来换取简洁。插入后检查实际缩放下的字号、重叠、裁切与箭头。

**交互图以 HTML 为源。** 每次新画或修改交互图，先交付可打开的 HTML；文档功能表仍可嵌入从该 HTML 导出的对应状态截图，并保留 HTML 文件或附件入口。需要点击、返回、切换或恢复的场景，在 HTML 中实现可演示操作；模拟状态和数值明确标作演示，不能冒充接口实测。

**先复用既有页面。** 已有 MasterGo、Figma 或产品页面时，先核对其入口、信息和状态，再补本次增量；写清在原页面新增什么，需要新增独立页面时再说明。项目特有的页面、阈值与业务规则留在项目上下文，不写成技能的通用事实。

## 实际修订中出现的问题

| 问题 | 修正与验收 |
|---|---|
| 为精简把规则压成两段长句 | 分组编号、一条一规则；逐项对照条件与异常是否保留 |
| 把设计稿日期当文档版本，把页面列表写进需求范围 | 文档版本与原型基线分开；范围按端及职责填写 |
| 模板章节全部补齐，夹带制作说明 | 遵从本次章节取舍，正文只留读者需要的信息 |
| 内测页切换时替换整个页面，普通反馈区消失 | 共享区持续渲染，测试所有相关状态及输入保留 |
| 功能表只有截图编号，或只提供 HTML 附件 | 每行嵌入具体截图，附件另行验证 |
| 多张图断开，缺少角色判断 | 按请求合并连续流程，逐分支对照功能表 |
| 把“□”文本或普通列表当成可勾选项 | 使用原生 checkbox；新写法在获准测试范围勾选、回读并恢复 |
| 改一句文字却重建整表，影响图片和列宽 | 优先替换单元格内文本块；保留未涉及内容，详见文档操作手册 |
| 更新后继续复用旧 block id | 重新 fetch，从最新结构定位，不靠历史下标继续写 |
| OAuth 过期就反复申请更多权限 | 判断具体失败接口；已有授权路径足够时完成并验证，不把额外授权当成完成标准 |
| 看到成功回执就宣布全部完成 | 分开报告回读、资源、实际交互、视觉检查及实机能力 |
| 截图失败后仍宣称排版已目检 | 检查当前页面和视口；有限排障，仍失败则保留语义与结构证据，明确视觉未验证 |
| 截图进程尚在运行就读取图片，误报文件不存在 | 先确认异步进程已完成及其退出结果，再读取产物；进程失败与路径错误分别处理 |

## 交付前检查

1. 对照最新确认，功能、流程、原型及验收口径一致；未决问题集中列明，不把等待超时当作同意。
2. 检查短句分层、标题连续编号和重点样式；逐条回读改动，对比其他单元格、图片、附件、画板及人工记录是否保持原样。
3. 原生勾选项保留实际验收状态；仅为交付文档而新增的待验收项保持未勾选，已有人工勾选状态按任务范围保留。
4. 真实原型交互、最终附件和视觉检查分别留证。无法截图时可确认结构、编号和文字，但不宣称已确认裁切、重叠或字体显示。
5. 清理仅限本次新增且可唯一定位的测试块；回读确认原内容恢复。交付正式入口、实际改动和未验证项。

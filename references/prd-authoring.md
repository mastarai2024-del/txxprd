# PRD 写法与交付检查

用于新写、改写需求描述，按原型补全或整理功能表。需求描述按下文的分层段落落稿；示例中的页面、阈值、权限和业务行为只属于示例，不是其他项目的默认需求。

## 文档命名与标题验收

文档名称是飞书顶部、目录和搜索中显示的名称，与正文的章节标题分开检查。动笔前查看同项目、同父目录的相邻需求，确认日期格式、分隔空格和主题写法；用户本次指定的名称优先。

- 同目录采用日期前缀时，沿用 `YYYYMMDD 需求主题`，日期与主题之间用一个空格。例如 `20261027 登录与验证码优化`。没有现成约定时也以此为默认格式，日期取实际编写日；不从截图时间、原型日期或未经确认的排期取值。
- 已有用户确认的标题和日期保持不变，日后修订不重置日期；用户明确要求改名时按新要求执行。模板名如“产品需求文档”“未命名文档”不算已确认名称，复制模板后应替换。
- 主题直接概括本次需求。项目已经由目录表达时，按相邻文档的习惯省略重复项目名及“需求文档／PRD”等套语；不自行添加业务版本或原型版本后缀。

通过 CLI 原地重命名，命令及回读方式见 [修改文档名称](feishu-docx-cli.md#修改文档名称)。修改后核对实际文档标题；Wiki 同时检查节点标题和父目录列表，保留原 node／document 标识与链接。只在正文新增大标题、只改附件名或只在回复中写出名称，都不算完成改名。

交付前检查名称是否符合本目录规则、是否仍有模板占位词，以及正文是否保持原样。仅改文档名称属于元数据调整，不改变正文业务版本；如果同时修改正文，按正文版本与变更记录规则处理。父目录不可读时，依据用户提供的目录截图核对，并说明目录回读未验证。

## 章节与版本

沿用本次文档的结构和明确取舍。常见章节这样填写：

| 部分 | 填写口径 |
|---|---|
| 前言、背景 | 简述当前问题、用户需要及本次目标，避免重复功能表 |
| 版本信息、变更日志 | 记录这篇文档的版本；保留人工填写的版本、作者和历史，原型版本放在原型说明中 |
| 需求范围 | 列涉及的端及职责，如 APP（Android／iOS）、设备、服务端；页面状态清单放到原型部分 |
| 功能说明 | 作为规则主体，条件、操作、结果和例外逐条写清 |
| 流程图、原型 | 涉及流程或界面变化时填写，与功能规则对应 |
| 验收、非功能要求 | 写可观察的结果和本次实际约束 |
| 埋点、项目规划、附录 | 有本次要求及资料时填写；用户明确暂不写的章节保持省略，不为填模板编造内容 |

有新原型或用户回复时，先核对基线和冲突。已删除、划线作废的旧规则不从历史材料补回；无法确定时提出具体问题，继续不依赖答案的部分。

文档名称与日期按上文处理。既有文档保留用户已确定的业务版本与历史；正文修订及格式调整的版本记录按 `SKILL.md` 的“每次改完都加变更记录”要求执行。

## 章节标题层级与编号

一级章节沿用当前模板。二级标题内部有独立分区时，分区使用三级标题并补齐数字序号；其下继续分区时用四级标题，依次类推。标题级别与编号深度同步，父章节编号保留，同级序号连续。

例如，以下是层级示例，不要求其他需求照搬章节名称或增设这些分区：

```xml
<h1>五、功能说明</h1>
<h2>5.1 产品流程图</h2>
<h3>5.1.1 注册流程</h3>
<h4>5.1.1.1 新用户</h4>
<h4>5.1.1.2 已有账号</h4>
<h3>5.1.2 密码管理</h3>
<h2>5.2 交互原型</h2>
```

使用飞书原生标题块，让分区进入文档大纲；字号、加粗或手打序号不能替代标题层级。自动编号与手写编号选一种，回读确认没有重复编号。功能规则内部继续使用下文的 `1 → a → i` 列表；只有承担章节导航作用的分区才升为标题，不把每条规则都变成标题。用户已经整理好的标题，以当前文档为准保留。

## 按页面或功能组织验收

- 先按读者实际检查的页面或功能划分验收组，为每组写对应层级的编号标题，并标注其关联的功能说明编号；不能将所有验收项堆成没有分组的长清单。
- 每条保留“前置条件 → 操作 → 可观察结果”，以可独立判定为准。共同前置条件可在组首说明；成功、取消、失败和边界路径按已确认需求拆开，便于定位不通过的功能。
- 多开关或多设备场景按本次规则检查状态组合、作用范围、目标对象及失败后原状态。字段仅展示、不可切换时，单独验收只读呈现和点击结果；不要默认所有设备或字段均可切换。
- 未确认的计时口径、恢复条件、通知渠道等继续留在对应待确认项，关联到验收组，不写成已确定标准。分组数量、条目数量与业务阈值取决于当前需求，不复用其他项目的数字。
- 勾选式清单使用原生 checkbox；已有人工结果保留，新增未验收项保持未勾选。文档回读、静态图、原型交互和真实系统联调分别报告。

例如，验收章节为一级标题时，页面组使用二级标题；如果组内还要分功能，则按上一节递增标题和编号：

```xml
<h1>六、验收标准</h1>
<h2>6.1 设备管理页（对应5.3第2项）</h2>
<checkbox done="false">前置：已进入当前设备的管理页。操作：点击仅作展示的设备名称。结果：不打开选择列表，不改变当前设备。</checkbox>
```

示例只演示写法，具体页面、交互及只读要求应来自当前确认。

## 写后格式验收

每次完成文档写入后，检查本次影响的章节、表格及相邻边界；只做文字修订也需要检查，不以命令成功代替排版验收。

1. **回读标题大纲。** 核对标题级别与数字编号一致、同级顺序连续，新增分区位于正确父章节。用户手工调整的标题不被旧内容覆盖。
2. **回读表格归属。** 检查表格行数、每行单元格数量、必要合并关系和列宽；新增记录确实位于目标表格内。尤其检查表格前后相邻段落，不能残留本应入格的版本记录或说明，也不能把新行写成单元格里的嵌套内容。
3. **检查网页显示。** 在飞书网页逐项查看受影响区域，核对边框、内容归列、编号缩进、换行、加粗、图片和附件。结构化回读与网页目检均通过后才能报告格式检查通过；网页不可访问时明确说明未验证，保留可恢复记录。
4. **修复后再交付。** 发现出格、错列或布局异常时按最小范围修复并重查；同时比较未涉及内容和已有人工结果。表格操作方法见 [表格局部修订](feishu-docx-cli.md#表格局部修订)。

## 需求描述的分层段落写法

这是所有新写、改写需求描述的默认格式，适用于功能表“功能详细说明”和正文中的业务规则。保留用户本次明确指定的其他格式。

- 模块：指出哪个部分，例如“记录选择”。
- 功能：一句话交代用途，例如“勾选需上传的记录”。
- 主规则：用 `1. / 2. / 3.` 编号，以简短句子说清对象和行为，例如“登录成功后在首页展示模式选择弹窗”。
- 分项：在对应主规则下，用 `a. / b. / c.` 缩进展开，每条独立成段；按本组实际需要写条件、操作、结果和例外，不机械凑齐固定分项数量。
- 规则粒度：一条表达一个可判断的规则，保留“条件 → 操作或结果”的联系。拆段后若条件只在上一分项出现，应在当前分项补回必要条件，避免把有条件的行为写成无条件行为。
- 层级：以两级为主；只有分项确需继续展开时才用 `i. / ii. / iii.`。单条短规则可直接作为主规则，不为凑层级增加空标题。
- 重点：关键条件、动作、禁止项和状态保留规则使用默认黑色粗体；普通解释保持常规字重。
- 交互图：本行放对应区域或状态的实际截图，尺寸以文字可辨、无裁切为准。

精简的目标是易读且完整。删掉重复解释，保留否定、数量、时间、选填／必填、保留／清空及失败后的处理。避免把多条规则压成长句，也避免把一个条件与它的结果拆成互不关联的碎句。

### 阅读效果

以下只示范排版，具体规则必须来自当前需求确认。飞书中的字母编号与缩进由原生列表生成：

```text
1. 登录成功后在首页展示“普通模式 / 未成年人模式”选择弹窗
   a. 默认不选。
   b. 首次登录或无法判断是否首次登录时均弹出。
   c. 已有展示记录则不再弹出。
   d. 不采集年龄或身份证信息。

2. 记录弹窗展示结果并处理关闭操作
   a. 展示时即按账号记录“已弹出”，不以完成选择为前提。
   b. 点击“暂不设置”时关闭弹窗，保持原模式。
   c. 后续登录或重启不再弹出。
```

其中 1.b 的展示条件、2.a 的记录时机及 2.b 的“保持原模式”是加粗重点。不要将整组说明全部加粗，也不要将截图中的蓝色编号延伸成蓝色正文。

### 对应 DocxXML

上例前两组规则可写成：

```xml
<ol>
  <li>登录成功后在首页展示“普通模式 / 未成年人模式”选择弹窗<ol>
    <li>默认不选。</li>
    <li><b>首次登录或无法判断是否首次登录时均弹出。</b></li>
    <li>已有展示记录则不再弹出。</li>
    <li>不采集年龄或身份证信息。</li>
  </ol></li>
  <li>记录弹窗展示结果并处理关闭操作<ol>
    <li><b>展示时即按账号记录“已弹出”</b>，不以完成选择为前提。</li>
    <li>点击“暂不设置”时关闭弹窗，<b>保持原模式</b>。</li>
    <li>后续登录或重启不再弹出。</li>
  </ol></li>
</ol>
```

每个主规则和分项都是独立的 `<li>` 块；子 `<ol>` 必须位于对应父 `<li>` 内。由飞书生成编号和续行缩进，不用手打字母、空格或 `<br/>` 拼出多级列表。写后检查实际 `seq-marker` 及网页层级：主规则为数字，分项为字母，各组分项重新从 a 开始。若显示为平级数字，应修正嵌套结构。

正式中文成稿使用可用的 `humanizer-zh` 审校；不可用时手工核对简洁性、语域与信息完整性。正文保留产品需求、待确认规则和必要的原型演示说明，制作过程、工具选择和测试日志放在交付记录中。

### 只整理段落时的完成标准

先对照原文确认每条业务规则都有去处，再按 [表格局部修订](feishu-docx-cli.md#表格局部修订) 修改目标单元格。回读编号、文字和加粗，核对未涉及内容；最后在飞书网页逐项目检。截图时让首条规则位于吸顶表头下方，长行分段查看，检查换行和续行缩进。回读成功与网页目检分别记录。

## HTML、截图与流程图

### 先读设计系统

制作原型前先按 [设计系统与 MasterGo](design-system-and-mastergo.md) 读取：

- MasterGo「设计规范」
- 最终版 After / V2 页面
- 同模块其他弹窗、表单和按钮状态

把色板、字号、圆角、间距、字体和按钮状态记录到 `design-baseline.md`。设计规范没读、最终画板没确认时，不开始写 HTML。

涉及新页面设计、视觉优化或界面评审时，配合已安装的 `txxui`，按其流程先读取并应用 Taste；已有 App 的设计规范和指定原稿仍是视觉基准。

**界面文案去重。** 对照标题、选项、按钮和辅助说明，只保留每处新增的信息；已在选项中表达清楚的意思，不在下方重复解释。保留必要的操作结果、限制和告知；删减后重新检查弹窗高度、按钮状态、触控范围及窄屏显示。

**界面说明写具体效果。** 面向用户直接说明功能变化和限制，例如“某项内容不可查看”，不要用“与某角色权限一致”代替效果说明。内部权限复用关系放在研发规则需要的位置，文案调整保留既有权限边界。用户要求去掉某类称呼时，检查本次受影响的页面提示、原型、配图和正文引用；该称呼限制只适用于确认的范围，不推广为其他项目的词语禁令。

**只读字段按只读呈现。** 本次需求明确名称或对象只用于展示时，使用普通文本，去掉选择框、下拉箭头及切换事件；设备切换只沿用已确认的其他入口。同步功能说明、原型、截图与验收项，并实际点击确认不弹出选择器、不改变当前对象及开关状态。不能只将选择框设为禁用后就声称已完成只读展示。

**共享区域与角色增量。** 原型中某角色是在通用页面下方增加内容时，把共享区作为持续存在的页面部分。切换页签、筛选、详情、上传进度和结果时，检查共享输入、按钮和联系信息仍在，未提交内容仍保留。检查最终 HTML 附件，不能只验证本地旧文件。

**有状态操作。** 按本次已确认规则检查筛选前后选择、备注、全选作用范围、跨筛选统计、取消、失败重试和恢复。用本地存储或计时器演示续传、锁屏上传时，说明它是演示；真实 APP 后台能力需实机验证。

**截图与附件各司其用。** 表格截图帮助逐项核对，HTML 附件用于交互。HTML 修改后重新生成受影响截图，核对最终附件的文件名、大小及预览交互，避免图片和附件版本错位。

**流程图保持业务连续。** 先确认主流程及角色／权限判断。用户要求合并时，把各段接成一条完整流程，包含关键判断、成功、失败和恢复分支。使用原生画板；静态预览或 SVG 导入成功不等于节点可编辑，需实际检查节点编辑能力。

### 文档同步与多版本一致

同一需求经常同时存在于飞书正文、功能说明表、流程图、原型截图、HTML 附件和 MasterGo 画板。任何一处改动都要按下面顺序检查，不能只更新最近打开的那份：

1. **确认变更源。** 先确认用户当前确认的是文档文案、MasterGo 画板还是 HTML 附件；不要用旧截图证明新规则，也不要用新 HTML 反推未确认的业务事实。
2. **列出所有引用位置。** 在文档中搜索同一状态、同一图片和同一附件，记录 block、表格行、章节或节点。只改一处很容易留下旧版本。
3. **按实际影响与依赖顺序更新。** 纯编号、缩进和段落整理只修改目标描述；业务或界面变化才同步受影响资产。规则先定稿，再更新设计稿和 HTML；HTML 定稿后统一渲染受影响截图，最后替换飞书图片和附件。
4. **回读结构。** 替换后重新 fetch，确认总览表、功能表、附件章节和正文引用都指向新资源；统计图片、附件和表格数量，避免局部替换后漏图。
5. **校验资源本身。** 下载当前文档实际引用的图片和附件，和本地文件比对 SHA-256。不要只根据上传成功或旧 token 判断；CDN 或缓存可能短暂返回旧内容。
6. **检查读者可见结果。** API 回读成功只证明结构存在；能登录飞书网页端时再做目检。懒加载图片刚进入视口时可能显示占位，等实际显示图加载完成后再判断；DOM 可读时可检查 `complete && naturalWidth > 0`，再目检图片内容。无法目检时明确写“结构和资源已回读，网页端视觉未验证”，不把本地截图写成网页端通过。

### 原型交互验收

- 交互原型至少覆盖来源页面、真实入口、弹层、取消/返回、保存或删除、结果反馈。
- 入口应在真实页面结构中可见，不要用“页面入口地图”、演示按钮或状态下拉替代业务入口。
- 测试脚本除了正常路径，还要覆盖取消、返回、重复点击和结果返回后的页面状态。
- HTML 附件与文档中的截图必须是同一版；附件替换后重新下载并比对哈希。
- 若真实 APP 的手势、后台任务、长连接或服务端能力未接入，原型只能标为交互演示，不能写成实机验收通过。

### 受限预览中的交互修复

用户说“按钮没反应”时，先在实际打开环境复现，再决定修复范围。飞书附件预览与本地浏览器可能有不同的表单、存储及视口限制。

1. **区分校验拦截与提交失效。** 检查输入是否合法、错误提示是否更新、提交处理是否执行及保存结果是否返回。非法输入被拦截不能据此判定按钮失效，也不能靠放宽业务校验让演示通过。字段重新编辑后清除或更新对应旧错误；保存失败保留输入并允许重试。必要的示例数据填充放在手机画面外，由用户点击原有保存按钮继续。
2. **确认宿主限制后再兼容提交。** 若原生表单提交确实被预览拦截，可让按钮点击和 Enter 进入同一客户端处理函数，保留输入校验与失败处理，并阻止重复的原生提交。检查已有监听器，避免叠加兼容逻辑导致重复保存或跳转；在当前云端附件内实际走通“非法输入→改正→保存失败→重试成功”。不要假定所有飞书预览都禁用原生表单。
3. **区分草稿与已保存数据。** 需要保留草稿时，按账号、设备和表单范围在重绘、弹层和返回后恢复；保存成功、重置及切换对象时按已确认规则处理，不能串用上一个对象的输入。敏感字段不因草稿机制写入持久存储。不同原型使用独立存储键；宿主禁用存储时仍允许本次会话操作，并提示刷新后进度不保留。
4. **按真实视口验收长页面。** 窄预览优先露出可交互画面，演示说明可排在画面后；不改动 APP 内的真实入口。保持实际手机视口并检查内部滚动、末条规则、保存按钮及底部安全区可达。文档长截图可以展示完整内容，但不能代替视口交互测试；位置断言需区分视口坐标、文档坐标和已有滚动量，不能把页面已滚动误报成布局错误。

### 设计稿独立图层

PRD 中的原型图如果取自 MasterGo，先确认目标画板里的图片是独立图层，而不是依赖来源文件的外部引用。回读时检查目标节点是否存在，截图是否有灰色占位、缺图或临时 URL；来源页面只读，复制后不能顺手改来源。来源与目标的节点、复制范围和清理条件记录在项目私有交付记录中。

| 看到成功回执就宣布全部完成 | 分开报告回读、资源、实际交互、视觉检查及实机能力 |

| 把 Before / 旧版当最终版 | 明确记录 After / V2 画板节点；无法判断时停止并向用户确认 |
| 只改主按钮颜色，选中态仍是旧棕色 | 同时核对主按钮、次按钮、选中、未选中、输入框和卡片 |
| 自创 18px / 20px / 24px 圆角和 13px / 15px 字号 | 收敛到规范字号与圆角；规范外数值需确认 |

| 画板导出报 `board:whiteboard:node:read` 缺失 | 按权限手册只申请该 scope；应用后台未开放时保留未验证状态 |
| 只更新交互原型章节，功能说明表仍是旧图 | 搜索同一资源的所有引用位置，按依赖顺序统一替换并回读数量 |

| 在只读来源画板上顺手调整了图层 | 立即停止后续写入，记录受影响节点并报告；不把来源修改当作目标交付 |

## 这两天项目复盘的可用结论

以下只沉淀可跨项目复用的判断，不把某次需求的页面、节点、日期、价格或 UI 示例当成通用规则：

- **文案校对与结构变更分开。** 只做文案校对时保留原章节、功能点和表格结构；需要补充业务规则时另开最小改动，不顺手重排全文。
- **用户选择的问题框要真用。** 业务规则有实质冲突时用当前环境的问题框；用户看不到问题应明确解释，而不是把答案写进文档后假定已确认。
- **事实、建议和未确认项分层。** 服务端日期、价格、剩余天数、端范围等规则必须以本次确认为准；设计占位数据、示例日期和网页截图只作展示。
- **文档同步以读者看到的版本为准。** API 回读、资源哈希和网页目检是三层证据；只完成其中一层时如实说明。
- **设计前先锁定设计源。** 最终 After / V2 画板、设计规范、同模块状态和字体可用性缺一不可；规范与页面冲突时记录并确认。
- **设计交付不等于产品上线。** 静态画板、可编辑图层、HTML 交互、文档写入和 APP 实机能力分别验收，互相不能替代。

## 交付前检查

1. 按[写后格式验收](#写后格式验收)检查标题层级、编号和表格入格情况，再对照最新确认核对功能、流程、原型及分组验收口径；未决问题集中列明，不把等待超时当作同意。
2. 逐条回读改动，确认所有受影响描述均采用数字主规则 + 字母分项、独立段落和必要加粗；局部整理时，对比其他单元格、图片、附件、画板及人工记录是否保持原样。
3. 原生勾选项保留实际验收状态；仅为交付文档而新增的待验收项保持未勾选，已有人工勾选状态按任务范围保留。
4. 真实原型交互、最终附件和视觉检查分别留证。无法截图时可确认结构、编号和文字，但不宣称已确认裁切、重叠或字体显示。
5. 清理仅限本次新增且可唯一定位的测试块；回读确认原内容恢复。交付正式入口、实际改动和未验证项。
